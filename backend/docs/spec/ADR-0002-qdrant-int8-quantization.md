# ADR-0002: Qdrant int8 스칼라 양자화 — 검색 지연 근본 수리

- **날짜**: 2026-08-13
- **상태**: 적용 완료(운영), 검증 완료
- **결정자**: 운영자 승인(원인 보고 후 "지금 적용" 선택)
- **관련**: CHANGELOG 2026-08-13(조사 로그 — RFC 문서는 해결 후 2026-09-29 삭제),
  CHANGELOG 2026-08-13 (3)

## 1. 배경 — 증상

- 베타 사용자 피드백(2026-08-05): "법령 검색 속도가 다소 느리다."
- fast 레인(POST /chat) 실측 프로파일(운영 컨테이너, 규제 질의 1턴):

  | 구간 | 시간 |
  |---|---|
  | PII 검사 + 의도판정 (병렬) | 0.6s |
  | 1차 LLM 콜(검색 도구 호출 생성) | 6s |
  | **검색(qdrant_search 도구)** | **11s** |
  | 답변 생성·스트리밍 | 9s |
  | **사용자 체감 합계** | **~27s** |

- 검색 API 단독 측정(캐시 미스 3연속): 12.47 / 6.30 / 7.55s.
  설계 당시 기록(웜 ~2.8s, 콜드 ~7.5s) 대비 **웜 상태에서 2~4배 회귀**.

## 2. 조사 — 단계별 소거

측정 체인(전부 2026-08-13 실측):

| # | 가설 | 측정 | 판정 |
|---|---|---|---|
| 1 | 리랭커 콜드 스타트 | keepalive(SEARCH_KEEPALIVE_S=240) 정상 가동 확인 + 웜 상태 연속 질의도 6~12s | 기각 |
| 2 | 네트워크(medi-back→DGX) | DGX localhost 직접 /search = 8.8s | 기각(서버 내부) |
| 3 | KURE 임베딩(:8001) | 직접 호출 0.008~0.2s | 기각 |
| 4 | 리랭커/조립 | 서버 로그 타임스탬프 분해 — qdrant 응답 후 완료까지 0.65s | 기각 |
| 5 | BM25 | qdrant 질의 **전** 구간이 6s — BM25는 qdrant 이후가 아님 → 5·6 분리 측정 | — |
| 6 | **Qdrant dense 질의** | 새 랜덤 벡터 + prod 필터: **6.9~10.0s**. 같은 벡터 재질의: **0.04s**(서버 시간 0.02s) | **확정** |
| 7 | DGX↔GCP WAN | RTT 3.8ms, scroll 100건+payload(240KB) 0.06s | 기각 |

핵심 증거는 #6의 비대칭 — **같은 벡터는 0.04초, 새 벡터는 7~10초**.
연산이 문제면 둘 다 느려야 한다. 이 패턴은 페이지 캐시 히트/미스의 서명이다.

## 3. 근본 원인

- 컬렉션 `articles_kure_v1`: 3,880,676 포인트 × 1024-dim float32,
  스토리지 **48GB** (GCP VM `instance-20260508-054141`의 openlaw-etl-qdrant-1).
- VM RAM **31GB**, 그중 Mongo 7.4GB(+CPU 85%)·Neo4j 2.5GB·qdrant 상주 4.4GB 등
  → page cache 가용 ~8GB.
- 48GB mmap 컬렉션이 캐시에 못 올라감 → **새 질의 벡터가 HNSW 그래프를 순회할
  때마다 디스크 랜덤 리드** = 질의당 6~10초. 재질의만 빠른 이유는 직전 순회가
  쓴 페이지가 아직 캐시에 남아서.
- 왜 회귀했나: 설계 시점("웜 2.8s") 이후 코퍼스 증가(가이드라인 컬렉션 추가·
  재임베딩)로 스토리지가 RAM 한계를 넘어섰다. `SEARCH_KEEPALIVE_S` 웜핑은
  리랭커 GPU 웜 전용이라 qdrant 페이지 캐시에는 무력(top_k=1 질의 하나로는
  그래프 전체를 못 데움).

## 4. 결정 — int8 스칼라 양자화 + always_ram

```
PATCH /collections/articles_kure_v1
{"quantization_config": {"scalar": {"type": "int8", "always_ram": true}}}
```

- float32 벡터(≈16GB)를 int8(≈4GB)로 압축해 **RAM 상주**. HNSW 순회가 디스크를
  안 탄다. 원본 float32 벡터는 디스크에 남아 리스코어링에 사용(정밀도 보존).
- 무중단: Qdrant 가 백그라운드에서 세그먼트 단위 재최적화(~40분, 서빙 중
  /readyz·실검색 정상 확인). 적용 중에도 기존 속도로 계속 서빙됐다.
- **원복 경로**: 같은 PATCH 로 `quantization_config` 제거 → 재최적화 후 종전
  상태. 데이터 무손실(원본 벡터 보존).

### 검토한 대안

| 대안 | 기각/보류 사유 |
|---|---|
| VM RAM 증설(31→64GB+) | 비용 지속 발생, 코퍼스 더 크면 재발. 양자화가 선행 |
| Qdrant 를 DGX 로 이전 | 데이터 로컬리티·대용량 메모리 이점 — 중기 후보로 RFC에 보류 |
| Mongo 메모리 상한(7.4GB) | 유효하나 부분 대책 — ETL 소유라 별도 협의 |
| medi-back 검색 프리페치 | 캐시가 질의 완전일치라 모델 재작성 질의에 미스 — 실익 작아 보류 |

## 5. 결과 — 실측

| 측정 | 전 | 후 | 배율 |
|---|---|---|---|
| Qdrant ANN(새 벡터, prod 필터) | 6.9~10.0s | 0.24~0.32s | ~30× |
| /search 왕복(medi-back, 캐시미스) | 6~12s | 0.97~2.25s | ~5× |
| fast 턴 검색 구간 | ~11s | ~3.9s | ~3× |
| **fast 턴 사용자 체감(done)** | **~27s** | **~22s** | −5s |

### 품질 검증 (eval_retrieval, 실버라벨 32질의, 적용 직후)

- MRR 0.720 · hit@1 0.594 · hit@3 0.844 · hit@5 0.938 · hit@10 0.969
- 베이스라인(MRR 0.75 · hit@1 0.65) 대비 소폭 하락. 단 ① 베이스라인 측정 후
  코퍼스가 증가했고 ② LLM-judge 실버라벨은 런 편차가 있어 **양자화 귀책 불확정**.
  hit@5 94% — 모델에 공급되는 상위 결과는 건강.
- 회복 여지: ETL 엔진 `_dense` 에 `oversampling`(2~3×)+`rescore` 파라미터 추가
  (RFC에 기재). 하락이 실사용 품질 신호(인용 신고·👎)로 확인되면 그때.

### 후속 — oversampling+rescore 적용 (2026-08-16)

품질 개선 프로그램 2단계로 적용(openlaw-etl `retrieval/engine.py _dense`,
`SEARCH_QUANT_OVERSAMPLING` 기본 2.0). 양자화 벡터로 후보 2배를 뽑아 원본
fp32 재채점 — 전후 동일 조건 실측(실버 32질의):

| 지표 | 전 | 후 |
|---|---|---|
| hit@1 | 0.594 | **0.625** |
| MRR | 0.720 | **0.740** |
| hit@5 | 0.938 | **0.969** |
| recall@10 | 0.788 | **0.837** |

쿼리당 지연 동일(~1.5s). 롤백 = env `SEARCH_QUANT_OVERSAMPLING=1.0`.

## 6. 운영 교훈

1. **저장소 크기와 호스트 RAM 을 함께 감시할 것** — 코퍼스는 ETL 이 계속
   키우는데(정상), 서빙 품질 저하가 "그날부터 느려짐"이 아니라 서서히 온다.
   `du /qdrant/storage` vs `free` 비율이 1을 넘으면 이번 증상이 재발한다.
   (후속: /readyz 또는 관측 지표에 이 비율 노출 검토)
2. **"같은 입력 반복=빠름, 새 입력=느림" 패턴은 캐시 미스 서명** — 연산(GPU·
   모델) 의심 전에 이 비대칭부터 확인하면 소거가 빠르다.
3. keepalive 류 웜핑은 **무엇을 웜하는지**가 명확해야 한다 — 리랭커 웜핑이
   있으니 콜드 문제는 없으리라 가정했지만, qdrant 페이지 캐시는 별개였다.
4. 이 컬렉션은 ETL 소유 — 운영 변경은 승인 후, 기록은 `etl_requests/` RFC 로.
   guide 컬렉션(docs_kure_v1)은 미적용 — 같은 증상이 보이면 동일 처방.
