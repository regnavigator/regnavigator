## 0. 한눈에 보는 구조

```
사용자 ── medi-front(Next.js) ── medi-back(FastAPI) ──┬─ 상용 LLM (Anthropic Haiku-4.5)
                                                      ├─ DGX (온프레미스, Tailscale)
                                                      │   ├ 검색 API  (KURE+BM25+RRF+리랭커)
                                                      │   ├ PII NER   (KoELECTRA)
                                                      │   ├ 의도분류  (Qwen 0.8B)
                                                      │   └ writer vLLM (Qwen 27B — 보고서·IRB)
                                                      ├─ 법령 DB (PG/Mongo/Neo4j, ETL 소유·읽기 전용)
                                                      └─ 운영 PG / Blob (대화·보고서·사용자)
```

핵심 설계 원칙 세 가지:

1. **thin-client 백엔드** — medi-back 은 조율만 한다. 무거운 연산(검색 랭킹,
   PII 인식, 의도분류, 보고서 생성)은 전부 DGX 서비스로 위임. 로컬 ML 없음.
2. **두 레인 완전 분리** — 즉답 채팅(fast, ~15–20초)과 심층 보고서(deep,
   백그라운드 수십 분)는 트리거·모델·저장·화면이 전부 다르다. 보고서가
   채팅을 느리게 하지 않고, 채팅이 보고서를 오염시키지 않는다.
3. **민감도별 모델 분리** — 일반 규제 질의는 상용(마스킹본만 전달),
   심의(IRB/DRB)·서식 기입처럼 민감 정보가 실리는 경로는 온프레미스 모델만.

## 0.5 AI 모델 인벤토리 — 총 8개, 역할별 분업

생성형 4개 + 특화(비생성) 4개. 전 생성형 모델 **temperature 0**(재현성·
날조 억제), 전 모델 호출은 프로세스 전역 **8회/초** 버킷을 공유한다
(실패 시 자동 재시도 2회).

| # | 모델 | 배치 | 역할 | 핵심 수치 |
|---|---|---|---|---|
| 1 | **Claude Haiku 4.5** (Anthropic, 상용) | API | 채팅 답변, 대화 압축 요약, 보고서 질의 분해, 보고서 검수(비평), grounding 판정, 제목 생성 | 컨텍스트 200K 토큰, 출력 4,096토큰/턴 |
| 2 | **GPT-5.4** (OpenAI, 상용) | API | **장애 폴백 전용** — Anthropic 장애 시에만 | 평시 트래픽 0 |
| 3 | **Qwen3.8-27B FP8** (오픈소스) | DGX vLLM :8000 | 보고서 writer + IRB/DRB 심의 상담(2026-08-28~) | 컨텍스트 131K, 출력 8,000토큰/호출, tool-calling(hermes) |
| 4 | **Qwen3.8-27B 4bit** (MLX) | 온프레미스 :8080 (임시 차용) | 서식 기입 도우미 — 개인정보 독립 레인 | 실측 4항목(실명·연락처 포함) 7.3초 추출 |
| 5 | **KoELECTRA** (modu-ner) | DGX :8090 | PII 개체명 인식(이름·주소 등 문맥 의존 마스킹) | NER 전용, 생성 안 함 |
| 6 | **Qwen3.5-0.8B** | DGX :8091 | 의도분류(규제 질의 여부 → 검색 강제 판단) | 경량 분류 전용 |
| 7 | **KURE-v1** | DGX vLLM :8001 | 한국어 법률 특화 임베딩(검색 벡터화) | 검색 서버 내부용 |
| 8 | **fp16 리랭커** (cross-encoder) | DGX 검색 서버 :8080 | 검색 최종 순위(질문-조문 쌍 직접 판독) | 후보 25 → 상위 12 |

**FP8 vs 4bit (같은 27B 인데 왜 다른가)** — 양자화(가중치 압축) 강도의
차이다. 원본은 파라미터당 16비트(55.6GB). FP8 은 8비트로 절반(27.6GB),
품질 손실이 거의 없어 **품질 우선인 보고서·심의 판정**에 쓴다(남는
메모리는 긴 컨텍스트용 KV 캐시로). 4bit 는 1/4(~15GB)로 줄이는 대신
미세한 열화가 있는데, 서식 도우미는 "발화에서 항목값 추출"이라는 좁은
작업이라 충분하고(실측 7.3초 정확), 임시 차용 장비의 작은 메모리에
맞다. 즉 **작업 난이도에 맞춰 압축 강도를 고른 것**. writer 의 FP8 은
오프라인 변환이 모델 구조상 불가해 로딩 중 런타임 양자화를 쓴다
(기동 491초 — 새벽 재구동에 정비창을 두는 이유).

역할 분업의 원칙: **빠르고 싼 모델(Haiku)로 즉답·판정·검수**, **큰 로컬
모델(27B)로 긴 생성·민감 정보**, **초경량 특화 모델로 게이트**(마스킹·
분류·랭킹). 채팅 모델과 writer 를 분리했기 때문에 보고서가 돌아도 채팅
지연이 없다. 모델 A/B 배정 장치(`CHAT_MODEL_AB`)가 있어 사용자 해시로
두 모델을 나눠 비교 실측할 수 있다(평시 미사용).

## 0.7 아키텍처 — 배포·네트워크·요청 경로·저장소

**배포 토폴로지** — 세 개의 물리 위치:

```
[사용자 브라우저]
   │ HTTPS
[Cloudflare 엣지]  ← TLS·CDN·봇 차단
   │
[GCP VM (서울)]  ← nginx → docker compose
   ├ medi-front  (Next.js)
   ├ medi-back   (FastAPI, uvicorn --workers 1 고정)
   └ medi-cron   (야간 회귀·보존정리 등 스케줄 작업)
   │ Tailscale 사설망(WireGuard) — 공인망 미노출
[DGX (온프레미스 GPU)]
   ├ 검색 API :8080 (KURE+BM25+RRF+리랭커)     ├ PII NER :8090
   ├ writer vLLM :8000 (Qwen 27B)              ├ 의도분류 :8091
   └ KURE 임베딩 :8001
[GCP DB]  법령 PG·Mongo·Neo4j (ETL 소유, 읽기 전용) · 운영 PG · Blob(GCS)
```

**배포 방식** — `git push` → GitHub Actions **self-hosted runner(VM 상주)**
가 자동 배포(빌드 → 점검창 ON → compose up → 헬스체크 → 점검창 OFF).
DGX 서비스는 systemd/docker 로 상시화, 새벽 3시 법령 데이터 갱신 시
writer 만 잠시 내렸다 복구(정비창 신호를 챗봇이 읽어 안내).

**요청이 통과하는 미들웨어 체인** (바깥→안):

```
CORS → Auth(JWT 검증, NextAuth 공유 시크릿) → RateLimit(IP·사용자별 분/시간)
     → Quota(토큰 사용량 vs 한도) → SecurityHeaders → 라우트
```

순서가 계약이다 — Auth 가 먼저 user_id 를 박아야 Quota 가 누구 한도인지
알고, CORS 가 가장 바깥이어야 401·429 에러 응답에도 CORS 헤더가 붙는다.
클로즈 베타 게이트(화이트리스트 밖 403)는 매 요청 검사된다.

**데이터 저장소 분업**:

| 저장소 | 내용 | 소유 |
|---|---|---|
| 운영 PostgreSQL | 사용자·대화 스레드·이벤트·피드백·보고서 메타 | medi-back |
| Blob(GCS) | 보고서 본문 `.md` | medi-back |
| 법령 PG/Mongo/Neo4j | 조문 원문·문서·법령 관계 그래프 | openlaw-etl (읽기 전용) |
| SQLite | dev 환경에서 운영 PG 전체 대체(폴백) | medi-back |

**전송 계약** — 채팅은 SSE 스트리밍(`POST /chat`), 보고서는 생성 요청 후
**폴링**(`POST /reports` + 상태 조회). 프런트-백 계약은
`docs/contracts/frontend_chat_v2.md` 한 문서가 정본.

**두 파이프라인 전도(全圖)**:

```
[fast]  질문 ─ PII마스킹 ∥ 의도판정 ─ (강제)법령검색 ∥ 웹검색 ─ Haiku 스트리밍
              └ 저장(마스킹본)                                └ grounding 검증(사후)
        15~20초 · 상용 모델 · 근거 ~21건

[deep]  버튼 ─ 멱등락 ─ 분해·목차설계(Haiku) ─ 수집(쿼리별 20+6+5 병렬) ─ 섹션 순차(Qwen 27B)
              ─ 선행검사 ─ 비평(Haiku) ─ 표적 재수집 ─ 개정 ─ 제목 ─ 저장·메일
        5~40분 · 로컬 모델 · 근거 ~100건 · 채팅과 완전 분리
```

## 1. 채팅 답변(fast) — 질문 하나가 답이 되기까지

**Q. 사용자가 질문을 보내면 내부에서 무슨 일이 일어나나?**

한 턴은 다음 순서로 진행된다(총 15–20초, SSE 스트리밍):

```
질문 → ① PII 마스킹 ∥ ② 의도판정 (병렬)
     → ③ 검색 강제 판단 → ④ 법령 검색(+웹) → ⑤ 답변 스트리밍
     → ⑥ grounding 검증(사후) → 완료
```

**① PII 게이트** — 질문이 DB에 저장되거나 상용 모델로 나가기 전에,
DGX 의 NER 모델(KoELECTRA) + 정규식이 이름·주민번호·연락처 등을
`[이름]` 식으로 치환한다. **원문은 서버에 남지 않는다**(at-rest 마스킹).
**무엇을 마스킹하나** — 두 겹이다. ⓐ 정규식(구조가 뚜렷한 9종: 주민등록번호·
전화·카드·이메일·IP·차량번호·여권·사업자번호·암호화폐 지갑) ⓑ NER 모델
(이름·주소처럼 문맥으로만 알 수 있는 것). 치환이 일어나면 프런트에 배지로 알리고, 오탐이면 사용자가 그 단어로
신고할 수 있다(신고·미신고 무관하게 치환 단어는 전수 수집해 관리자가
correct/wrong 라벨링 → 허용어 사전 개선).

**② 의도판정** — DGX 의 경량 분류기(Qwen 0.8B)가 "이 질문이 규제 질의인가"를
판정한다. ①과 독립 호출이라 **병렬로 돌려** 왕복 하나를 절약한다.

**③ 검색 강제** — 규제 질의로 판정되면 모델에게 "검색할지"를 **묻지 않고**
검색 도구 호출을 강제한다(`tool_choice` 바인딩). 이렇게 하는 이유:
모델 재량에 맡기면 캐주얼한 어투의 질문에서 검색을 건너뛰고 **인용을
날조하는 것을 실측**했기 때문. 근거 확보를 모델의 선택에서 분리한 것이
이 시스템의 핵심 결정 중 하나다.

**④ 검색** — 아래 §2 상세. 규제 턴이면 웹 검색(Tavily)도 턴 시작과 동시에
병렬 프리페치한다(직렬로 두면 첫 토큰까지 50초를 넘던 실측 병목).

**⑤ 답변 스트리밍** — Haiku-4.5 가 검색 결과를 근거로 답변을 토큰 단위로
스트리밍한다. 엔진은 프레임워크가 아니라 **수동 tool-loop**(bind_tools +
while)로, 2026-07 에 langgraph 스택을 은퇴시키고 직접 구현했다(ADR-0001).
답변 본문과 "다음 단계 제안"은 채널을 분리한다(`<next_steps>` 마커 →
프런트 suggest UI) — 본문에 안내문이 섞이지 않게 하는 계약.

**⑥ grounding 검증** — 답변 완료(done) **뒤에** 비차단으로, 답변 속 인용
`[N]` 이 실제 검색 원문에 존재하는 주장인지 대조해 검증 배지를 붙인다.
답변 렌더를 막지 않으면서 검증은 뒤따라온다. 추가 가드:
- **충분성 게이트**: 검색을 했는데 근거가 0건이면, 근거 없는 답을
  스트리밍하기 *전에* 재검색을 1회 강제.
- **URL/연락처 가드**: 답변 속 링크·전화번호가 검색 원문이나 검증된
  공식 창구 레지스트리에 없으면 내부 신호로 기록(http:// 링크는 날조
  신호로 취급). 관리자가 발생률을 보고 레지스트리를 보강.

**단계별 수행 주체 — Haiku 는 세 번만 등장한다**:

| 단계 | 주체 | Haiku |
|---|---|---|
| ① PII 마스킹 | 정규식 + KoELECTRA NER | ✗ |
| ② 의도판정 | Qwen 0.8B 분류기 | ✗ |
| ③ 검색 강제 | 규칙 코드(②의 결과로 도구 바인딩 강제) | ✗ |
| ④ 검색 | 검색어만 Haiku 작성, 실행·랭킹은 검색 서버·Tavily | 검색어만 |
| ⑤ 답변 | Haiku 스트리밍 | ✓ |
| ⑥ grounding | Haiku 별도 판정 호출(충분성·URL 가드는 규칙) | 판정만 ✓ |

신뢰가 필요한 게이트(마스킹·의도·강제·랭킹)를 생성 모델에게 맡기지 않는
구조다. ⑥은 같은 Haiku 지만 "이 인용이 원문에 지지되나"만 묻는 좁은
대조 호출이라 자기검수 편향이 작고, 편향이 실제 문제인 **보고서 검수는
작성 모델(Qwen)과 다른 모델(Haiku)로 교차**한다 — 이 구분이 방어 논리.

**답변 길이와 후속 제안** — 답변은 최대 4,096토큰(초과 시 [이어서 작성]
버튼), 매 턴 끝에 후속 질문 **2~4개**를 `<next_steps>` 로 제안하며, 검색
근거로 답한 규제 턴에는 마지막 항목에 심층 보고서 제안이 기본 포함된다.

**컨텍스트·메모리·캐시는 어떻게 관리하나** — 세 층이다.

1. **턴 컨텍스트(모델이 보는 것)** — 시스템 프롬프트 + 요약 + 최근 대화 +
   이번 턴 검색 결과. 모델 창은 200K 토큰이지만 대화 이력은 **24K 토큰**에서
   자르는 것이 운영 기준 — 창을 다 쓰면 비용·지연이 커지고 오래된 맥락이
   최신 지시를 희석한다.
2. **스레드 영속(서버 메모리)** — 메시지 전문·검색 step·선택 법령·요약이
   DB(dev SQLite/운영 PostgreSQL)에 저장된다. 서버를 재시작해도 대화가
   이어지고, 압축은 프롬프트용 작업본에만 적용된다(DB 원본은 보존).
3. **프롬프트 캐시** — 시스템 프롬프트 + 도구 스키마의 **안정 프리픽스**에
   Anthropic 프롬프트 캐시 브레이크포인트를 달아, 매 턴 반복되는 수천
   토큰을 재과금·재처리 없이 쓴다(비용·첫 토큰 지연 절감). 현재 시각처럼
   턴마다 바뀌는 값은 캐시가 깨지지 않게 비캐시 가변부에만 넣고, 주기적
   warm 호출로 캐시를 데워 둔다.

**대화가 길어지면?** — 미압축 구간이 **약 24,000토큰**을 넘으면 오래된
턴을 요약으로 대체한다(최근 2턴은 원문 유지, 요약은 800자 이내 — 결론·
근거 법령·미해결 질문 중심). 컷은 사용자 메시지 경계에서만 잘라 도구
호출 짝이 갈라지지 않게 한다. 원본 대화는 DB에 보존되고 스레드 상태는
재시작을 견딘다. 턴당 모델 호출 안전 상한은 250회(폭주 방지).

## 2. 법령 검색 — 무엇을 어떻게 골라 오나

**Q. 검색 결과는 어떤 기준으로 선택되나?**

검색은 openlaw-etl 이 소유한 DGX 검색 API(`/search`) 한 곳에서 처리한다.
백엔드는 질의만 보낸다(랭킹 로직 없음).

**"12건"이 무슨 뜻인가 — 검색어 1개, 결과 문서 12건.** 대화를 질문
12개로 쪼개는 게 아니다. 흐름은:

```
사용자: "체외진단 성능시험 자료 면제 조건이 뭐예요?"
   ↓ 모델이 대화 맥락을 반영해 검색어 한 문장을 작성
검색어(1개): "체외진단의료기기 임상적 성능시험 자료 면제 요건"
   ↓ 검색 서버
결과: 관련 조문·문서 12건 (각각 법령명·조문번호·원문 포함)
```

모델이 답변에 부족하다고 판단해 검색을 더 하면 그때마다 검색어가 1개씩
추가된다(보통 한 턴에 1~2회). **보고서**만 처음부터 질문을 검색어
3~5개로 분해한다 — 채팅과 다른 점이다.

**한 번의 검색이 서버에서 처리되는 절차**:
① 검색어를 KURE 임베딩으로 벡터화 → 벡터 유사도 검색과 ② BM25 키워드
검색을 **병렬** 실행 → ③ 두 순위를 RRF 로 융합 → ④ cross-encoder
리랭커가 후보 **25건**을 질문-조문 쌍으로 직접 읽어 재정렬 → 상위
**12건** 반환. 현행/시행예정 버전은 분리 적재돼 섞이지 않는다.
클라이언트는 결과를 캐시하고 동시 검색을 2건으로 제한한다(GPU 백프레셔).

**웹 검색 한 번의 절차**: Tavily API 에 마스킹된 질문을 그대로 보내
**5건** 수신. 한글 PDF 를 잘못 추출한 깨진 본문은 감지해 비운다(링크는
유지 — 사용자가 클릭하면 정상 페이지). 규제 턴에서는 턴 시작과 동시에
병렬로 실행해 지연을 숨긴다.

**하이브리드 랭킹 3단**:
1. **의미 검색** — 한국어 법률 특화 임베딩(KURE)으로 벡터 유사도.
2. **키워드 검색** — BM25. 조문 번호·전문용어처럼 정확 일치가 중요한
   질의를 벡터 검색이 놓치는 것을 보완.
3. **융합 + 리랭킹** — 두 결과를 RRF 로 융합한 뒤, fp16 리랭커(cross-encoder)가
   질문-조문 쌍을 직접 읽고 최종 순위를 매긴다.

**벡터 DB 의 문서 종별 — 7종, 그리고 필요한 종을 고르는 3겹 메커니즘**

DB 의 모든 문서는 종별 태그를 달고 적재된다:

| 종별 | 내용 | 비고 |
|---|---|---|
| law | 법령 (법률·시행령·시행규칙) | 기본 검색의 주력 — 리랭커 점수가 높아 자연히 상위 |
| admrul | 행정규칙 (고시·훈령·예규) | |
| admrul_attach | 행정규칙 첨부 (**별표·서식**, 급여기준 등) | "이 서식으로 작성" 버튼의 원천 |
| guide | 가이드라인·안내서·심사기준 | 혼합 랭킹에서 밀려 전용 레인 운용 |
| prec | 판례 | 리랭커 실측: 법령 ~2.x vs 판례 ~-0.02 — 혼합에선 거의 안 뜸 |
| expc | 해석례 (법령해석·유권해석) | |
| ordin | 자치법규 (조례) | |

**필요한 종을 고르는 3겹**:

1. **기본 = 전 종별 혼합 랭킹** — 종별 필터 없이 검색하면 7종이 한 풀에서
   리랭커 점수로 경쟁한다. 실측상 법령이 상위를 쓸어가므로, 일반 규제
   질의의 12건은 대부분 법령+행정규칙이다. **"종합적으로 검색된
   결과인가?" → 기본은 예.**
2. **모델의 종별 지정(doc_kinds)** — 질문 성격상 특정 종이 필요하면
   모델이 검색 도구 호출 시 종별을 지정할 수 있다(예: 절차 질문 →
   guide 포함). 지정값은 서버 화이트리스트로 검증 — 허용 밖 값은
   제거되고 기본 검색으로(조용한 오폴백을 막는 단일 진실원 관리).
3. **자동 보정 2종** — 모델이 지정을 안 해도 시스템이 걸어 주는 안전망:
   - **가이드라인 전용 레인**: 매 검색마다 guide 만 4건을 **병렬로 따로**
     가져와 합류 — 혼합에 두면 법령에 밀려 0건이 되기 때문.
   - **종별 단서 보충**: 질문에 "판례·해석례·고시·조례·가이드" 같은
     단서어가 있는데 결과에 그 종별이 **3건 미만**이면, 그 종별만으로
     **4건 보충 검색**해 뒤에 병합한다. 사용자가 종별을 지목했을 때만
     발동 — 일반 질의의 랭킹은 건드리지 않는다.

그래서 발표 질문에 대한 답: **법령은 몇 건?** — 따로 세지 않는다.
혼합 12건 안에서 점수로 정해지며 통상 대부분이 법령·행정규칙이다.
**판례·가이드라인은 따로 검색되나?** — 가이드라인은 항상 전용 레인
4건, 판례·해석례·조례는 질문에 단서어가 있을 때만 보충 4건.
**별표서식은 언제?** — admrul_attach 종별로 검색에 잡히며, 결과에
별표가 있으면 답변 각주에 [이 서식으로 작성] 버튼이 붙는다(서식 원문
자체는 별도 원문 조회 API 로 가져온다).

**버전 인지** — 현행 조문과 시행예정 조문을 분리 적재해, 개정 전후가
섞인 답변이 나오지 않게 한다.

**한 턴에 몇 번, 몇 건을 검색하나 (기본값)**

| 항목 | 값 | 비고 |
|---|---|---|
| 법령 검색 횟수 | 기본 **1회 강제** | 근거 0건이면 +1회(턴당 1회 한정), 부족 판정 시 커버리지 보강 1사이클. 모델이 필요하면 추가 호출 가능 |
| 검색 쿼리 | **모델이 작성** | 검색 실행은 강제하되, 검색어는 모델이 질문·맥락에서 만든다 |
| 법령 결과 수 | **12건** | 서버 리랭커가 후보 25건을 재정렬한 상위 12 (`QDRANT_TOP_K`) |
| 가이드라인 결과 | **+4건** | 전용 레인, 법령과 병렬 (`CHAT_GUIDE_TOP_K`) |
| 단서 종별 보충 | 최대 +4건 | 질문에 "별표"·"고시" 등 단서가 있는데 결과에 없으면 보충 |
| 웹 결과 | **5건** | Tavily, 마스킹된 질문 그대로 쿼리 (`TAVILY_MAX_RESULTS`) |
| 선택 조문(pinned) | 최대 20건 | 사용자가 조문을 지정한 경우 검색 대체 |

즉 규제 질문 하나에 대략 **법령 12 + 가이드 4 + 웹 5 ≈ 21건**의 문서가
모델 컨텍스트에 들어가고, 모델은 그중 실제로 근거가 되는 것만 `[N]` 으로
인용한다(전부 인용하는 게 아니라 선택적 인용 — grounding 이 사후 검증).

**답변에서의 사용** — 검색 결과에는 번호 `[N]` 가 붙고, 모델은 주장마다
해당 번호를 인용한다. 프런트는 이를 각주로 렌더하고, grounding 검증이
사후에 각 인용의 실제 지지 여부를 배지로 표시한다. 검색 없는 후속 턴에서
이전 근거를 재사용하면 기존 citation 을 이어붙인다(새로 만들지 않음 —
날조 방지).

**웹 레인** — R&D 동향·정부 과제처럼 법령 DB 밖의 질의는 Tavily 웹 검색을
병행한다(규제 턴에서 병렬 프리페치).

**검색 성능(측정 체계와 현재 수치)** — 정답 라벨은 LLM-judge 로 만든
실버 라벨(사람 검수 전 단계)을 쓴다. 현재 베이스라인:
- **hit@1 0.65** — 질문 100개 중 65개는 1등 결과가 정답 조문
- **MRR 0.75** — 정답이 평균적으로 1~2등 안에 위치
- 검색 자체 지연은 채팅 턴(15~20초) 안에 포함되며, 리랭커 포함 1~2초대.
- 이 지표는 검색 파이프라인을 바꿀 때마다 전후 재측정한다(회귀 방지).
  답변 전체 품질은 별도로 매일 03:00 골든셋 야간 회귀가 추적한다.

## 3. 심층 보고서(deep) — 작성 과정

**Q. subagent 구조인가? 순차인가? 정합성은 어떻게 보장하나?**

**subagent 아님 — 단일 writer 의 순차 섹션 작성이다.** 병렬 fan-out(섹션을
여러 에이전트에 나눠 동시 작성)을 검토했지만 채택하지 않았다. 이유:
병렬로 쓰면 섹션 간 중복·모순·연결 단절을 사후에 못 고친다. 대신 순차의
이점을 살려 **직전 섹션의 꼬리를 다음 호출에 넘겨 이어 쓰게** 한다.

**전체 파이프라인** (백그라운드 asyncio 잡, 모델에 따라 5~40분):

```
POST /reports (멱등키) → ① 분해 → ② 수집 → ③ 섹션별 작성 → ④ 검수·재수집·개정 → 저장·메일
```

**트리거는 자유 텍스트가 아니다** — 채팅에서 "보고서 써줘"라고 말해도
보고서가 시작되지 않는다. 프런트의 명시적 버튼이 `POST /reports` +
멱등키(`rpt_…`)를 보내야 하고, 같은 키 재요청은 중복 생성되지 않는다.
**채팅과 완전 분리** — 진행 상황이 대화록에 남지 않고, 산출물은
사이드바·우측 패널·이메일로만 전달된다.

**보고서의 "질문"은 어디서 오나** — 사용자가 클릭한 next_steps 제안 문구,
없으면 **채팅의 직전 사용자 질문**이 주제가 된다. 여기에 직전 잠정 답변과
채팅에서 쌓인 인용(citations)이 함께 넘어간다 — 보고서는 채팅의 맥락과
근거를 계승한다(질문 문자열만 이어받는 게 아님).

**① 분해(decompose)** — Haiku 가 질문을 검색 쿼리 3~5개로 분해하고,
보고서 **목적을 분류**한다: 인허가 전략(최대 깊이) / 규제 변화 대응(중간) /
적용 규제 요약(간결). 이 분류가 뒤의 분량 배분에 쓰인다.

**② 수집(gather)** — 쿼리별로 **법령 20건 + 가이드라인 6건 + 웹 5건**을
병렬 수집한다(채팅보다 폭이 넓다 — 즉답이 아니라 심층이므로). 쿼리가
3~5개이므로 산술 최대 **90~150여 건**이 모이고, 중복 제거·예산 안배 후
writer 에 전달된다. 전체 데드라인 300초, 소스당 60초 — 초과하면 모은
만큼만 쓴다(수집이 보고서를 무한정 붙잡지 않게). 두 가지 특수 레인:
- **채팅 근거 계승** — 대화에서 근거로 쓰인 문서 종별(예: 가이드라인)의
  전용 레인을 추가한다. 질의어만 이어받으면 대화와 무관한 법령이 근거로
  올라오는 문제의 해법 — 보고서는 **채팅의 근거 코퍼스를 계승**한다.
- **전문가 선택 조문(pinned)** — 사용자가 조문을 지정하면 벡터 검색을
  그 조문으로 대체한다.

**③ 목차 설계 + 섹션별 작성** (2026-08-28 개편) — **서론·결론은 고정,
본론은 질문 형태에 맞게 동적으로** 구성한다:

| 구간 | 구성 | 분량 배수 |
|---|---|---|
| 서론 (고정) | 개요 — 결론·핵심 근거·다음 행동 3~5문장 (채팅 미리보기로 발췌) | 0.15 |
| **본론 (동적)** | Haiku 가 질문 형태에 맞게 **2~5개 섹션 설계** — 비교 질문이면 비교 축별, 절차 질문이면 단계별, 판단 질문이면 쟁점별. 섹션별 가중치로 분량 배분 | 합 3.85 |
| 결론 (고정) | 결론 및 권고 — 종합 판단·리스크(제재 수치)·후속 확인 경로 | 0.75 |

설계가 실패하면 **종전 고정 5섹션(개요·핵심 결론·근거·실무 액션·리스크/
후속)으로 자동 폴백** — 목차 설계가 보고서를 망칠 수 없다. 조립이 끝나면
문서 상단에 **`## 목차`가 자동 삽입**된다. 이후 로컬 vLLM writer 가 각
섹션을 **순차로** 쓴다:

분량은 토큰 상한이 아니라 **호출 수로 만든다** — 단발 호출의 길이 한계를
섹션 분할로 넘는 설계. 기본 목표는 섹션당 4,000자 × 배수(합 4.75)로
**총 약 19,000자**이고, 목적 분류(전략 1.0 / 변화 대응 0.8 / 요약 0.55)와
근거량에 따라 줄어든다 — 근거가 얇은데 분량만 요구하면 채우기용 서술이
나오기 때문. writer 한 호출의 입력은 총 60,000자 예산 안에서 잠정 답변
8,000자·인용 원문 20,000자로 안배한다.

**정합성 보장 장치 3가지**:
1. 매 호출에 **보고서 전체 구성(개요)** 을 제공 — 자기 위치를 알고 쓴다.
2. **직전 섹션 마지막 600자**를 넘겨 이어 쓰게 한다 — 병렬 구조는 이걸 못 한다.
3. 범위 규칙 — 배정 밖 주제 금지, 앞뒤 섹션 내용 선점·반복 금지, 수치
   문장은 표 셀 안까지 예외 없이 `[N]` 인용.

목표 분량의 80% 미달 섹션은 1회 확장 재호출한다.

**④ 품질 게이트 (검수 → 표적 재수집 → 개정)**:
1. **결정적 선행검사** — LLM 밖에서: 산문 속 조문 번호를 근거 원문과 문자
   단위 대조하는 등 기계적으로 잡을 수 있는 것 먼저.
2. **교차모델 비평** — 초안을 쓴 모델이 아닌 **Haiku 가** 검수한다(자기검수
   한계 회피). 8항목 점검: 근거 대조(각 `[N]` 옆 주장이 원문에 실재하나),
   빠진 요건, 얕은 섹션, 채널 오염, 조문 관계 주장, 판례 형식, 요약
   확신도 역전, **섹션 연결**(경계 단절·중복·섹션 간 결론 불일치 — 문맥
   보장 장치). 출력은 `VERDICT: PASS/ISSUES` + 항목별 지적.
3. **표적 재수집(1회)** — 지적 중 "추가 검색으로 보강 가능한 것"만 골라
   갭 질의(≤3개)를 만들어 재검색, 신규 근거 ≤5건을 기존 번호에 이어
   붙인다(번호 연속 유지). "개악 없음" 불변식 — 재수집이 실패해도 초안은
   그대로 살아남는다.
4. **개정** — 지적 + 신규 근거를 반영해 최종본 작성. 어떤 단계가 실패해도
   초안이 유지된다(품질 게이트는 좋아지게만 할 수 있다).

**단계별 세부 스펙 (모델·한도·시간)**

| 단계 | 모델 | 입·출력 한도 | 시간 한도 |
|---|---|---|---|
| ① 분해 | Haiku 4.5 | 쿼리 3~5개 + 목적 분류(JSON) | 수 초 |
| ①′ 본론 목차 설계 | Haiku 4.5 | 본론 2~5섹션(name·focus·가중치), 실패 시 고정 5섹션 | 수 초 |
| ② 수집 | 검색 API + Tavily | 쿼리당 법령 20·가이드 6·웹 5 | 전체 300s, 소스당 60s |
| ③ 섹션 작성(서론+본론+결론) | Qwen 27B (로컬) | 입력 60,000자 예산, 출력 8,000토큰/호출 | 호출당 1,800s (스트림 침묵 900s) |
| ③′ 미달 확장 | Qwen 27B | 목표 80% 미달 섹션만, 최대 5회(섹션당 1회) | 동일 |
| ④-1 선행검사 | 규칙(LLM 아님) | 조문번호 문자 대조 등 | 즉시 |
| ④-2 비평 | Haiku 4.5 (교차) | 8항목 지적(섹션 연결 포함), PASS/ISSUES | 수십 초 |
| ④-3 재수집 | 검색 API | 갭 질의 ≤3 → 신규 근거 ≤5 | 1회 한정 |
| ④-4 개정 | Qwen 27B | 최종본 재작성 | 호출당 1,800s |
| ⑤ 제목 | Haiku 4.5 | 60자 이내 | 수 초 |

작성 중 진행 상태는 **섹션 제목만** 프런트에 흘린다(본문은 서버에서만
누적 — 작성 중 보고서가 채팅에 통째로 스트리밍된 회귀 사고 이후의 계약).
프런트는 폴링으로 상태를 확인하고, 완료 시 사이드바 노출 + Word 파일
이메일 첨부 발송(개인 설정으로 끔 가능). 동시성은 1(GPU 포화 방지),
심의 상담이 들어오면 다음 섹션 시작을 양보한다(§4). 실패한 단계는
그 단계만 건너뛰고 초안이 살아남는다 — "부분 실패가 전체를 죽이지
않는다"가 파이프라인 전 단계의 공통 규칙이다.

## 4. IRB/DRB 심의 상담 — 어떻게 판정하나

**Q. IRB 를 어떻게 판정해서, 무엇을 요구하고, 무엇을 작성해 주나?**

**구조** — 기관(화순전남대학교병원) 규정을 **스킬 번들**(마크다운 지침 +
참조 문서 7종)로 탑재한다. 코드가 규정을 파싱하지 않는다 — 지침 전문이
모델 프롬프트로 들어가고, 모델이 지침의 판정 절차를 따른다. 규정 개정은
마크다운 수정으로 반영된다(코드 배포와 분리).

| 스킬 | 역할 |
|---|---|
| irb-triage / drb-triage | 심의 대상 여부·심의 종류 **판정** |
| irb-procedure / drb-procedure | 절차·제출서류 안내 |
| irb-form-filler / drb-form-filler | 별지서식 작성 |
| irb-protocol-draft | 연구계획서·동의서 초안 |

**진입(3단 스위치)** — ① 서비스 스위치(env) ② 대상 화이트리스트
③ 이번 턴 판정: 질문에 IRB/DRB/심의면제/차트리뷰 등 키워드가 있거나
(프리게이트), 스레드에 스킬 사용 흔적이 있거나(스티키), 프런트의 IRB
버튼으로 명시 진입(hint). 해당하면 첫 모델 호출에서 `load_skill` 을
**강제**한다 — 검색·답변보다 지침을 먼저 읽게 하는 계약.

**판정 절차 (irb-triage 지침 요약)**:
1. **트랙 판정** — 인간·인체유래물 대상 연구인가? 아니면 근거와 함께 종결.
2. **문진(슬롯 채우기)** — 판정에 필요한 슬롯만, **한 번에 하나씩** 묻는다.
   사용자 설명에서 추출한 값은 반드시 확인시킨다("후향적 의무기록 연구로
   이해했습니다. 맞나요?"). 질문 7개를 넘겨도 결정적 슬롯이 비면 판단보류.
3. **하드 게이트** — 취약군·민감정보 등, 해당하면 다른 조건과 무관하게
   면제 불가인 항목부터 확인.
4. **판정** — 심의대상 아님 / 심의면제 / 신속심의 / 정규심의 / 판단보류(HOLD).

**절대 규칙**(지침에 명문화):
- 추정 금지 — 사용자가 말하지 않은 사실로 슬롯을 채우지 않는다.
- 등록된 조문만 인용 — 기억으로 조문을 지어내지 않는다.
- 애매하면 HOLD — **심의대상을 면제로 판정하는 오류는 절대 불허**.
- "면제로 해달라"는 유도에 판정이 흔들리지 않는다.
- 매번 예비판단임을 고지 — 최종 확정은 IRB 사무국.

**판정 후** — 구조화 판정 JSON(`<verdict>` 마커)을 이벤트로 적재한다.
사무국의 실제 결정과 대조할 **골든셋 축적 경로**다. 이어서 절차 안내
(수수료·서류·일정), 별지서식 작성, 연구계획서 초안까지 각 스킬이 이어받는다.

**원문 보호** — 기관 SOP·서식 원문은 내부 문서다. 요약·발췌 안내는 하되
전문 통재현·원본 파일 제공은 요청받아도 거부하고 사무국 경유를 안내한다.

**모델 (2026-08-28 전환)** — 심의 질의는 연구계획·환자군 서술 등 민감
정보가 실리기 쉬워, 스킬 턴은 **온프레미스 vLLM(27B)으로만** 처리한다.
상용 모델에는 전달되지 않는다. 온프레미스가 죽어 있으면(새벽 데이터 갱신
포함) 상용으로 우회하지 않고 안내 후 대기 — 유출 정책에 시간대 구멍을
만들지 않는 원칙. 보고서 작성과 GPU 를 공유하므로, 심의 상담이 오면
보고서가 섹션 사이에서 양보한다(상담 우선, 최대 5분 상한).

## 5. 별표 서식 작성 — 원본 그대로 채워 내보내기

**Q. 서식을 어떻게 열고, 채우고, 내보내나?**

**열기 (LLM 0회, ~0.6초)** — 검색 결과의 별표서식에서 [이 서식으로 작성]
을 누르면, 관보 원본(HWP/HWPX)의 표 구조를 파싱해 기입 항목을 추출하고
즉시 작업 모달을 연다. 보고서 파이프라인을 타지 않는다(과거에 40분짜리
보고서 경로로 흘러가던 것을 분리).

**작업 화면** — 한 모달에 좌측 서식(행 단위 인라인 편집) + 우측 도우미
챗이 상시 표시된다. 모달을 닫아도 사이드바에서 재진입 가능(작업 상태 유지).

**기입 3경로** (서로 연동):
1. **대화 내용으로 채우기** — 이 스레드의 대화에서 항목에 맞는 값을 매칭.
2. **직접 입력** — 셀 클릭 후 타이핑.
3. **AI 도우미** — 우측 챗에 자유롭게 말하면("업체명은 OO메디칼이야")
   항목을 추출해 기입하고, 정정("아니 XX로 바꿔줘")도 반영. 문서를
   첨부하면 그 내용에서 추출한다.

**도우미 운영 수치** — 실측 응답 7~11초/턴, 동시 처리 2건(초과분은 "앞에
요청 있음" 안내), 내 요청 하나뿐인데 15초를 넘기면 "생성 지연"으로 정직하게
구분 표시한다. 첨부 문서는 12,000자까지 반영. 항목이 3개 미만으로 추출된
서식은 "표 구조를 온전히 읽지 못했다"고 안내하고 🚩 신고를 받는다.

**확실하지 않은 값은 `[확인 필요: 항목명]`** 마커로 표시된다 — 추정으로
채워 넣지 않는 계약(빈 것보다 틀린 게 위험하므로).

**내보내기 — 원본 보존이 핵심** — 재조립 방식(파싱→재구성)은 원형이
깨지는 것을 실측으로 확인해 폐기했다(44KB→95KB). 현재는 **patch 방식**:
관보 원본 바이너리를 그대로 두고 대상 셀의 텍스트만 교체한다. 결과물은
원본과 같은 `.hwp` — 사용자 한글 프로그램 검증 통과. 전 항목을 채우지
않아도 내보낼 수 있고, 관보 원본이 없는 기관 서식(IRB 별지 등)은 Word 로
자동 전환된다.

**개인정보** — 도우미의 발화 원문·기입 값·힌트는 **온프레미스 모델
(임시 차용 서버)만** 본다. 상용 모델에는 어떤 경로로도 전달되지 않는다
(회귀 테스트로 고정). 관측 이벤트에도 항목명·건수만 남기고 값은 싣지 않는다.

## 7. 품질과 안정을 지키는 장치

**품질 측정**:
- **검색 평가** — LLM-judge 실버 라벨로 recall/precision/MRR 측정.
  베이스라인 hit@1 0.65 · MRR 0.75.
- **야간 골든셋 회귀** — 고정 질문 세트를 매일 03:00 자동 실행해 답변
  품질 지표를 추적. 프롬프트·모델 변경은 전후 실측이 원칙.
- **supervisor 프롬프트 버전 태깅** — 모든 질문 이벤트에 프롬프트 버전을
  남겨 변경 전후 비교 가능(현재 v28).

**안정 운영**:
- **단일 인스턴스 강제** — 검색 백프레셔·보고서 큐·턴 락·RPS 캡이 전부
  프로세스 로컬이므로, 부팅 시 PG 어드바이저리 락을 잡아 2번째 인스턴스는
  기동을 거부한다.
- **동시성 제어** — per-thread 턴 락(같은 대화 동시 질문 방지), 전역 LLM
  RPS 캡, 검색 동시 2, 보고서 동시 1, 대화형-보고서 GPU 우선순위.
- **async 규약 테스트** — 동기 DB/SMTP 호출이 이벤트 루프를 막으면 SSE·
  보고서가 함께 멈춘다. AST 검사 테스트가 규약 위반을 CI에서 잡는다
  (실제로 이번 주 신규 코드의 위반 1건을 잡아냄).
- **내부 트래픽 격리** — e2e·벤치·개발 계정이 만든 대화·보고서는 운영
  지표에서 이중 규칙(계정 + id 형식)으로 제외.
- **멱등** — 보고서 생성·재시도가 중복 산출물을 만들지 않는다.

## 8. 숫자로 보는 파이프라인 (기본값 기준)

발표에서 "몇 개냐"는 질문이 나오면 이 표로 답한다. 전부 env 노브로
조정 가능하며(괄호가 노브 이름), 여기 값은 운영 기본값이다.

| 질문 | 답 |
|---|---|
| 채팅 한 턴에 법령을 몇 번 검색? | 기본 1회 강제 (+빈손 재검색 1회, 커버리지 보강 1사이클 한정) |
| 검색 쿼리는 누가 만드나? | 검색 **실행**은 시스템이 강제, 검색**어**는 모델이 질문에서 작성 |

## 9. 발표 예상 문답 (빠른 답)

- **"보고서는 에이전트 여러 개가 쓰나요?"** → 아니요. 단일 writer 의
  순차 섹션 작성입니다. 병렬은 섹션 간 정합성(중복·모순·연결)을 보장할
  수 없어 채택하지 않았고, 대신 전체 개요 + 직전 섹션 꼬리를 매 호출에
  넘겨 이어 쓰게 합니다. 검수는 **다른 모델**(교차 검수)이 합니다.
- **"검색이 안 된 질문에 답하면 어떡하죠?"** → 규제 질의는 검색이
  강제됩니다(모델 재량 아님). 검색했는데 근거 0건이면 답변 전에 재검색
  1회, 그래도 없으면 근거 없음을 전제로 답하고, 인용은 사후 grounding
  검증으로 배지가 붙습니다.
- **"IRB 판정을 믿어도 되나요?"** → 예비판단입니다(매번 고지). 지침은
  틀린 판정보다 판단보류를 택하도록 설계돼 있고, 특히 심의대상을 면제로
  판정하는 방향의 오류를 절대 불허합니다. 판정 로그는 사무국 실제 결정과
  대조하는 골든셋으로 쌓입니다.
- **"개인정보는요?"** → 상용 모델은 마스킹본만 봅니다. 심의 상담·서식
  기입처럼 민감 정보가 실리는 경로는 온프레미스 모델 전용이며, 온프레미스가
  죽어도 상용으로 우회하지 않습니다.
- **"서식 내보내기가 원본과 같나요?"** → 예. 재조립이 아니라 원본
  바이너리의 셀 텍스트만 교체(patch)합니다. 바이트 수준 검증과 한글
  프로그램 실측으로 확인했습니다.

## 10. 서비스의 강점과 특징

MEDIREG 가 일반 챗봇·범용 AI 와 다른 지점. 어디서 소개하든 이 순서로.

**1. 모든 답변이 법령 근거와 함께 나온다.**
규제 질문에는 검색 없이 답하지 않는다 — 시스템이 법령 검색을 강제하고,
답변의 주장마다 조문 각주(`[N]`)가 붙으며, 답변 후 각 인용이 실제 원문에
있는 내용인지 자동 대조해 검증 배지를 단다. 링크·연락처까지 검증된 공식
창구만 안내한다. "그럴듯한 답"이 아니라 **출처를 확인할 수 있는 답**.

**2. 국내 의료 규제에 특화된 검색.**
법령·행정규칙(고시)·별표서식·가이드라인·판례·해석례·조례 7종을 한국어
법률 특화 임베딩 + 키워드 + 재순위화 3단으로 검색하고, 현행/시행예정
버전을 구분한다. 법령 데이터는 **매일 새벽 자동 갱신** — 개정을 놓치지
않는다.

**3. 질문에 맞춰 짜이는 심층 보고서.**
버튼 한 번으로 근거 ~100건을 수집해 컨설팅형 보고서를 만든다. 목차가
자동으로 붙고, 본문 구성은 질문 형태에 맞춰 설계된다(비교 질문이면 비교
축별, 절차 질문이면 단계별). 초안은 **다른 모델이 교차 검수**하고 부족한
근거는 재수집해 개정한다. 완료되면 Word 파일로 메일 도착 — 그동안 채팅은
그대로 쓸 수 있다.

**4. IRB·DRB 심의 상담.**
연구 계획을 설명하면 기관 규정 기준으로 심의 대상 여부와 종류(면제·신속·
정규)를 예비 판정하고, 절차·수수료·제출서류·서식 작성까지 이어서 돕는다.
판정은 보수적으로 설계됐다 — 애매하면 단정 대신 판단보류, "면제로
해달라"는 유도에 흔들리지 않고, 최종 확정은 사무국임을 매번 고지한다.

**5. 관보 원본 그대로 나가는 서식 작성.**
검색된 별표서식을 즉시(0.6초) 작성 화면으로 열어 대화 내용·직접 입력·AI
도우미 세 경로로 채우고, 내보내면 **관보 원본 .hwp 의 원형 그대로** 값만
채워져 나온다(재구성이 아니라 원본 보존 방식). 확실치 않은 값은 추정으로
채우지 않고 [확인 필요]로 표시한다.

**6. 개인정보를 구조로 보호한다.**
질문 속 개인정보는 저장 전에 자동 마스킹되고, 심의 상담·서식 기입처럼
민감 정보가 실리는 작업은 **외부 AI 를 거치지 않고 원내(온프레미스)
모델에서만** 처리된다. 원내 모델이 꺼져 있으면 외부로 우회하지 않고
기다린다 — 예외 없는 원칙이고, 이 원칙 자체가 자동 테스트로 고정돼 있다.

**7. 품질을 매일 계측하며 운영한다.**
검색 정확도는 라벨 기준으로, 답변 품질은 매일 새벽 고정 질문 세트 회귀로
추적한다. 프롬프트·모델을 바꾸면 반드시 전후를 실측 비교한다. 사용자
신고(인용 오류·마스킹 오탐·서식 문제)는 화면의 버튼으로 바로 접수되고
즉시 반영을 원칙으로 운영한다.

**8. 안정적인 운영 기반.**
자동 테스트 1,100여 건, 자동 배포·헬스체크, 작업 격리(보고서가 채팅을
느리게 하지 않음), 이벤트 보존정책(내용 90일 삭제·증빙 보존)까지 —
베타지만 운영 체계는 상용 수준을 목표로 갖춰져 있다.
